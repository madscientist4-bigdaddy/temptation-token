## 2. The finding that changes the picture: **the token is not a proxy**

`CLAUDE.md`, the SolidProof questionnaire and the live `/audit` page all describe the
token as a UUPS proxy whose v2 implementation (`0xb995b63c…`) shipped the M-1 fix on
2026-05-17. That is not what is deployed.

**Evidence, three independent ways:**
1. `proxiableUUID()` **returns successfully** on `0x5570eA97…`. OpenZeppelin marks that
   function `notDelegated`; through a real proxy it reverts. The staking proxy, checked
   the same way, *does* revert with `"UUPSUpgradeable: must not be called through
   delegatecall"` — so the test discriminates correctly.
2. The EIP-1967 implementation slot on the token reads **zero**.
3. The token holds **20,747 bytes** of code. An ERC1967 proxy is ~170 bytes, as the
   staking proxy is.

**Three consequences.**

**(a) The M-1 zero-value-transfer fix is not live.** Executed on a fork between two
non-exempt addresses:
```
transfer(B, 0)  ->  revert: panic 0x11 (arithmetic underflow)
```
The fix in `TTS_v2_M1fix.sol` is `require(amount > 0, "TTS: zero transfer not allowed")`.
Mainnet panics instead of returning that string, so the deployed code predates the fix.
The v2 contract exists at `0xb995b63c…` (21,004 bytes, different codehash) and **nothing
delegates to it.** It is orphaned.

*Impact:* a zero-value `transfer`/`transferFrom` reverts. Accounting loops, some router
and Safe batch patterns, and several integrations perform zero-value transfers as a
matter of course. ERC-20 requires them to succeed. **Severity: Medium** — a real
interoperability defect, no fund risk.

**(b) It cannot be fixed.** Not by upgrade — there is no proxy. Part 5.5 of the sprint
(remove the blacklist gate, hard-cap the tax, make MINTER non-grantable) is therefore
**not executable as an upgrade.** It would require deploying a new token and migrating
holders, which is out of scope for this sale and probably not worth doing.

**(c) It is also the single best thing about this token.** An immutable token removes the
largest centralization risk a buyer would otherwise flag. It should be presented that way
— but presented *accurately*, which means retiring the "UUPS proxy" language everywhere.

## 4. Timelock (Safe transaction #2)

**Scope is smaller than planned, because the token is not upgradeable.** A timelock on
UPGRADER_ROLE for the *token* is theatre — the role is inert. What the timelock must
actually cover, in order of how much it matters:

1. **DEFAULT_ADMIN_ROLE on the token** — this is what makes A-1 real. Behind a 48h
   timelock, granting MINTER_ROLE becomes a publicly visible 48-hour-notice event rather
   than a two-signature surprise. This is the single most valuable governance change
   available, and it is the one a buyer will ask about.
2. **UPGRADER_ROLE on the staking proxy** — genuinely upgradeable, genuinely worth
   delaying.
3. Trophy NFT admin, as applicable.

**Deploy:** OpenZeppelin `TimelockController`, `minDelay = 172800` (48h),
proposers = `[Safe]`, executors = `[Safe]`, admin = `address(0)`.

⚠️ **Do not renounce the Safe's DEFAULT_ADMIN_ROLE until a full grant → wait → execute
cycle has been proven through the timelock on a fork.** `DEFAULT_ADMIN_ROLE` is its own
role admin; renouncing it while the timelock is misconfigured is **irreversible and
would permanently freeze every admin function on the token** — including
`setTaxExempt`, which the liquidity work depends on. Build it, fork-prove the whole
cycle, then have Jim approve the renounce as a separate step.

**Status: not built in this pass.** Safe tx #1 (liquidity) must execute first, and the
renounce risk above deserves its own fork test rather than being bundled.

## 7. Addendum — 2026-09-25, found during the claim-verification pass

### A-12 — Supabase **anon** key was hardcoded in two committed scripts
`scripts/deployV3.js` (since 2026-04-22, `f2859b1`) and `scripts/seed-tts-posts.js` (since
2026-05-03, `4abd35f`) each carried the project's Supabase **anon** JWT as a string literal.

**Severity: Low**, and the reasoning matters because a buyer will find it in git history and
ask.
- The token's `role` claim is **`anon`**, not `service_role`. An anon key is designed to be
  client-visible; it is what ships in a typical Supabase frontend.
- Its reach is bounded by RLS, and RLS is **verified ON** with policies present on every
  PII table: `users`, `submissions`, `verified_submitters`, `bonus_claims`, `votes`,
  `age_acknowledgments`, `verified_wallet_links`, `admin_config`.
- No `service_role` key, wallet private key or Bridge credential appears anywhere in the
  tracked tree — checked by pattern across the whole repository.

**Done:** both literals replaced with `process.env.SUPABASE_ANON_KEY`.
**Still to do, and it is the actual remediation:** removing it from `HEAD` does not remove
it from history. **Rotate the anon key in the Supabase dashboard at handover** (one click,
Settings → API) and hand the buyer a clean one. Until then, treat the committed value as
public — which, given RLS, it effectively always was.

### A-13 — `bonus_claims` has RLS enabled but **zero policies**
RLS on with no policy means deny-all for anon, which is the safe direction and is what the
security model wants. Recorded only so nobody later reads "0 policies" as a gap and adds a
permissive one.
