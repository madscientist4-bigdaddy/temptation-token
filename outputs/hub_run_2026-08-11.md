## 2. TOKEN ROLES — renounce options (REPORT ONLY, nothing executed)

**Live role state, read on-chain 2026-08-11** — `TTS 0x5570eA97…`, Base 8453:

| Role | Holder | Note |
|---|---|---|
| `DEFAULT_ADMIN_ROLE` | **Safe only** (`0xeFb59d88…`) | Bank revoked |
| `UPGRADER_ROLE` | **Safe only** | Bank revoked |
| `PAUSER_ROLE` | **nobody** | zero members |
| `MINTER_ROLE` | **nobody** | zero members |
| `paused()` | `false` | — |

The capabilities still exist **in the code** (mint, pause, blacklist-gate). What changed
is that nobody currently holds the keys to two of them. That distinction is the whole
subject of this table: an empty role set is *reversible*, because `DEFAULT_ADMIN` can
re-grant it at any time. Only a renounce is permanent.

### What each renounce buys, and what it forecloses — permanently

| # | Action | Makes permanently true | Forecloses — permanently |
|---|---|---|---|
| A | Renounce `MINTER_ROLE` (already empty) | nothing new on its own | nothing — **cosmetic**, `DEFAULT_ADMIN` can re-grant tomorrow |
| B | Renounce `PAUSER_ROLE` (already empty) | nothing new on its own | nothing — same re-grant path |
| C | **Renounce `DEFAULT_ADMIN_ROLE`** | no role can ever be granted again ⇒ **mint and pause become permanently impossible** | `setTaxExempt` (new contracts can never be exempted — every future voting/staking contract pays the 1% tax on every transfer), `setTreasury`, all future role administration |
| D | **Renounce `UPGRADER_ROLE`** | implementation can never change ⇒ nobody can add a blacklist setter or re-introduce mint via upgrade | **all future fixes.** A discovered bug is unfixable forever. No migration path |
| C+D | Both | the strongest honest claim available: "cannot be minted, cannot be paused, cannot be upgraded, blacklist has no setter and one can never be added" | everything in C and D combined — the token becomes fully immutable and fully unmaintainable |

### The trade, stated plainly

- **C alone** is the one that converts "no mint/no pause" from a *current fact* into a
  *permanent fact*. It is also the one that breaks `setTaxExempt` — which this project
  relies on every time a new contract is deployed (staking needed it in August). Doing C
  before the contract set is final would tax every future system transfer at 1%.
- **D alone** kills upgradeability. Note the Safe is proposer *and* executor on the
  staking timelock, so D removes the only remaining path to patch the token itself.
- **A and B are close to theatre.** Renouncing an already-empty role changes nothing an
  auditor can rely on, because C is what makes it stick. Announcing A or B as "we
  renounced mint" would be the same category of overstatement the Blockaid correction
  exists to walk back.

**Recommendation (not executed):** do nothing until the contract set is frozen. When it
is, C+D together, executed in one Safe batch, is the only combination that supports a
clean immutability claim. Until then the honest public line is: *"mint and pause exist in
code; no address currently holds either role; the Safe could re-grant them."*

## 5. WORDPRESS 301 REDIRECT — exact click steps

Goal: `temptationtoken.io/audit` → the corrected audit page, without leaving the stale
V3b / dead-proxy content reachable.

### Option A — Hostinger hPanel (no plugin, survives theme changes)
1. hpanel.hostinger.com → log in.
2. **Websites** → `temptationtoken.io` → **Dashboard**.
3. Left sidebar → **Advanced** → **Redirects**.
4. **Redirect type:** `301 (Permanent)`.
5. **Redirect from:** select `temptationtoken.io`, path box → `/audit`
   *(no trailing slash, no `https://` — the path only).*
6. **Redirect to:** paste the full destination URL, e.g.
   `https://temptationtoken.io/transparency`.
7. Click **Create**. It appears in the list below within ~30 seconds.
8. Verify — in Terminal:
   `curl -sI https://temptationtoken.io/audit | head -3`
   You want `HTTP/2 301` and a `location:` header pointing at the new URL.
   If you see `200`, WordPress served the old page and the redirect did not take.

### Option B — inside WordPress (if hPanel Redirects is unavailable)
1. `temptationtoken.io/wp-admin` → log in.
2. **Plugins → Add New** → search **Redirection** (by John Godley) → Install → Activate.
3. **Tools → Redirection** → run the setup wizard (accept defaults).
4. **Add new redirection**:
   - Source URL: `/audit`
   - Target URL: `https://temptationtoken.io/transparency`
   - Group: `Redirections`
   - Click the ⚙ gear → **HTTP code: 301 — Moved Permanently**
5. **Add Redirect**.
6. Same `curl -sI` verification as above.

### Gotchas that actually bite
- **Cache.** If Hostinger LiteSpeed/Cloudflare cache is on, purge it or you will keep
  seeing the old 200 for up to an hour. hPanel → **Advanced → Cache Manager → Purge**.
- **Trailing slash.** WordPress canonicalises `/audit` → `/audit/`. Create the rule for
  `/audit`; verify BOTH forms with curl.
- **Do not delete the old page** until the redirect is confirmed working — deleting first
  gives a 404, which is worse for the scanner reviews than a stale page.

## 6. TRANSAK — build state and YOUR signup steps

### Build state: SEAM ONLY, deliberately

`src/config/buy.js` is committed. It exports `BUY_ENABLED`, which is **false** and
requires *both* `VITE_BUY_ENABLED=true` *and* a present `VITE_TRANSAK_API_KEY`. There is
no widget, no SDK dependency, and no network call to Transak yet.

That is on purpose: the integration cannot be written honestly until the account exists,
because the widget's available assets, fees and KYC tier all come from the approved
account. A speculative integration would ship copy we would have to retract.

**One thing to know before you start:** Transak does not list $TTS, and will not. The only
truthful flow is *card → ETH/USDC on Base → swap to $TTS on Uniswap*. `BUY_DISCLOSURE` in
the config already states this. Any "buy $TTS with a card" copy would be false — and given
the liquidity truth table (a $100 swap pays ~10% slippage), the swap leg needs its own
warning before this goes live.

### Your steps — Transak business signup

1. **transak.com** → top right **Get Started** / **For Business** → **Sign up**.
2. Create the account with `jim@temptationtoken.io` (not a personal address — the
   dashboard is the API-key holder of record).
3. **Company details.** You will need:
   - Legal entity: `Blockchain Entertainment LLC`
   - Registered address (the same UPS-box/registered-agent address as `MAIL_ADDR`)
   - Jurisdiction of incorporation + registration number
   - Website: `https://app.temptationtoken.io`
4. **Compliance questionnaire.** Expect: business model description, source of funds,
   expected monthly volume, and whether you serve US persons. Answer honestly — an
   inconsistency here is what stalls approval.
   - Describe the product as: *a weekly on-chain contest where users purchase governance
     tokens to cast votes.* Do **not** describe it as gambling or as an investment.
5. **KYB documents.** Certificate of formation, EIN letter, and a government ID for
   every beneficial owner ≥25%.
6. **Integration settings** (after approval): set **allowed networks** = Base,
   **allowed crypto** = ETH, USDC, and add `app.temptationtoken.io` to the domain
   allowlist. Without the domain allowlist the widget refuses to load.
7. **API keys** → copy the **STAGING** key first. Give me both keys and I will wire the
   widget behind the existing flag and test on staging before anything touches production.

**Timeline:** KYB review is typically 3–10 business days. Nothing in the app changes until
you set the env vars, so there is no deadline pressure on our side.

**Cost:** no setup fee. Transak takes a per-transaction fee from the buyer (typically
~0.5–5% depending on payment method and region) — you are not billed directly.
